# Arc Loom — Software Requirements Specification

**Version:** 1.0
**Status:** Baseline for weeks 1–12
**Convention:** MUST / SHOULD / MAY per RFC 2119. Requirements marked **[Wn]** are introduced in that week and MUST NOT be implemented earlier.

---

## 1. Purpose and scope

This SRS specifies a personal news storyline-tracking system. It covers ingestion, two-level clustering, storyline linking, development detection, personalized ranking, notification gating, and the evaluation harness that measures all of the above.

It does not cover: user-generated content, payment, multi-tenancy beyond invite-only accounts, mobile-native applications, or content hosting.

### 1.1 Actors

| Actor | Description |
|---|---|
| **Reader** | Consumes the feed and storyline views. Sets interests. Receives notifications. |
| **Operator** | Runs the pipeline, edits `feeds.yaml`, tunes thresholds. Same physical person as Reader in v1. |
| **Pipeline** | The unattended scheduled process. |
| **Labeler** | The Operator acting in evaluation mode, producing gold-standard data. |

## 2. Functional requirements

### 2.1 Feed configuration (FR-100)

**FR-101 [W1]** The system MUST read feed configuration from a single `feeds.yaml` file at startup. Adding, removing or re-tagging a feed MUST NOT require a code change or a schema migration.

**FR-102 [W1]** Each feed entry MUST support: `name`, `url`, `packs` (list of strings), `enabled` (bool, default true), `weight` (float, default 1.0), `lang` (ISO 639-1, default `en`).

**FR-103 [W1]** The system MUST validate `feeds.yaml` on load and fail loudly with the offending entry named. It MUST NOT silently skip malformed entries.

**FR-104 [W1]** A feed that fails to parse on N consecutive runs (N configurable, default 20) MUST be flagged `degraded` in the database and reported, but MUST NOT halt the pipeline.

**FR-105 [W9]** A pack MUST be selectable by a Reader as a starter bundle. Selecting a pack MUST expand into individually editable interests, not an opaque subscription.

### 2.2 Ingestion (FR-200)

**FR-201 [W1]** The system MUST fetch feeds over HTTPS using conditional requests, sending `If-None-Match` and `If-Modified-Since` when a prior `ETag` or `Last-Modified` is stored. A `304` response MUST be recorded and MUST NOT trigger reprocessing.

**FR-202 [W1]** The system MUST send a truthful, contactable `User-Agent` identifying the project and providing a contact URL. It MUST NOT impersonate a browser or another crawler.

**FR-203 [W1]** The system MUST respect `robots.txt` for every host it contacts, cached with a TTL of at least 24 hours.

**FR-204 [W1]** The system MUST NOT fetch, store, or process full article body text. Permitted fields are: title, feed-provided summary/description, canonical URL, publication timestamp, author, and feed-provided tags.

**FR-205 [W1]** The system MUST enforce a per-host politeness delay (default 2s) and a global concurrency cap (default 8).

**FR-206 [W1]** Timestamps MUST be normalized to UTC. Where `published_at` is absent or unparseable, the system MUST fall back to `fetched_at` and set a `timestamp_inferred` flag.

**FR-207 [W1]** URLs MUST be canonicalized before deduplication: strip `utm_*`, `fbclid`, `gclid` and fragment; lowercase host; resolve one level of known redirect wrappers.

**FR-208 [W1]** An article whose canonical URL already exists MUST be discarded, not updated.

**FR-209 [W2]** Ingestion MUST be idempotent. Running the pipeline twice over the same feed state MUST produce identical database contents.

### 2.3 Near-duplicate filtering (FR-300)

**FR-301 [W2]** The system MUST compute a 64-bit SimHash over title character-trigrams for every article.

**FR-302 [W2]** Articles within Hamming distance ≤ 3 of an existing article from the last 72 hours MUST be attached to that article's cluster directly, bypassing embedding computation.

**FR-303 [W2]** The syndication bypass rate MUST be logged per run as a pipeline health metric.

### 2.4 Embedding (FR-400)

**FR-401 [W2]** The system MUST compute embeddings locally using a sentence-transformers model. No embedding API calls are permitted. Rationale: evaluation requires unlimited re-embedding of the full corpus.

**FR-402 [W2]** The embedding input MUST be the title concatenated with the first two sentences of the feed summary, truncated to the model's context limit. Title-only embedding is explicitly prohibited — headlines are too short and too stylized for reliable cross-source matching.

**FR-403 [W2]** Embeddings MUST be L2-normalized at write time so that similarity is a plain dot product at read time.

**FR-404 [W2]** Embeddings MUST be stored as `float32` BLOBs in SQLite. A dedicated vector database MUST NOT be introduced before a measured query-latency justification exists.

**FR-405 [W2]** The active embedding model identifier MUST be stored alongside each embedding. A model change MUST invalidate and trigger recomputation rather than mixing vector spaces.

### 2.5 Event clustering — Level 1 (FR-500)

**FR-501 [W2]** The system MUST assign every article to exactly one event cluster.

**FR-502 [W2]** Clustering MUST be incremental and single-pass. Historical articles MUST NOT be reprocessed on each run.

**FR-503 [W2]** A new article MUST be compared only against centroids of clusters with activity in the preceding 72 hours (configurable `ACTIVE_WINDOW_H`).

**FR-504 [W2]** If the best-matching centroid exceeds threshold `TAU_EVENT`, the article joins that cluster and the centroid MUST be updated as the running mean of member embeddings. Otherwise a new cluster is created.

**FR-505 [W2]** `TAU_EVENT` MUST be a configuration value, not a literal. Its shipped value MUST be justified by a published sweep against the gold set (see FR-1100).

**FR-506 [W2]** Cluster canonical title MUST be selected as the title of the member article from the highest-`weight` source, ties broken by earliest `published_at`.

**FR-507 [W3]** The system MUST expose a cluster's source count and distinct-source count. Distinct-source count is the coverage signal shown to Readers.

### 2.6 Entity extraction (FR-600)

**FR-601 [W4]** The system MUST extract named entities from each cluster's canonical title and member snippets, typed as at minimum: PERSON, ORG, GPE, LAW, EVENT, PRODUCT.

**FR-602 [W4]** Extraction MUST use a local NER model as a first pass. An LLM pass MAY refine and canonicalize the entity set, but MUST be folded into an existing LLM call where one exists rather than adding a new one.

**FR-603 [W4]** Entities MUST be canonicalized to a surface-form-independent key (e.g. "OpenAI", "OpenAI Inc.", "OpenAI, Inc." collapse to one identifier). Canonicalization MUST be persisted in an alias table so it is inspectable and correctable by hand.

**FR-604 [W4]** Each cluster MUST store a weighted entity set: entity identifier plus a salience score derived from position (title > snippet) and frequency across members.

**FR-605 [W4]** The system MUST maintain a stoplist of entities too common to carry linking signal within a pack (e.g. "United States" in a US-politics pack). The stoplist MUST be derived from corpus document frequency, not hand-written.

### 2.7 Storyline linking — Level 2 (FR-700)

**FR-701 [W5]** The system MUST link event clusters into storylines. Every cluster belongs to exactly one storyline; a storyline contains one or more clusters ordered by time.

**FR-702 [W5]** Link scoring MUST be a weighted combination in which **entity-set Jaccard similarity is the dominant term**, embedding cosine similarity is secondary, and recency is a multiplicative decay. Embedding-only linking is explicitly prohibited. Rationale: semantic similarity is uncorrelated with narrative identity — clusters about one organization may be unrelated narratives, and clusters within one narrative may be semantically distant.

**FR-703 [W5]** Linking MUST be incremental. A new cluster MUST be scored against live storylines only; storylines dormant beyond `STORYLINE_TTL_D` (default 45 days) MUST be excluded from candidate scoring.

**FR-704 [W5]** If no candidate exceeds `TAU_STORY`, the cluster MUST seed a new storyline.

**FR-705 [W5]** Storyline entity sets MUST be maintained as a decayed union of member cluster entity sets, so that a storyline's identity drifts with the narrative rather than being fixed at seeding.

**FR-706 [W5]** The system MUST support manual merge and split of storylines by the Operator, with the action recorded. These corrections form training/eval signal and MUST NOT be silently overwritten by the next pipeline run.

**FR-707 [W6]** A storyline MUST be renderable as a chronological timeline showing each constituent cluster with its date, canonical title and source count.

**FR-708 [W6]** A storyline MUST carry a human-readable title, initially the seeding cluster's canonical title, updatable by later logic or by hand.

### 2.8 Summarization and state (FR-800)

**FR-801 [W7]** The system MUST generate at most one LLM summary per event cluster. Per-user or per-interest summarization is prohibited — it breaks the cost amortization property.

**FR-802 [W7]** Summaries MUST be at most two sentences and MUST be generated only from titles, feed-provided snippets and cross-source agreement.

**FR-803 [W7]** Summary generation MUST be idempotent and cached by cluster identifier and member-set hash. A cluster gaining members MAY be re-summarized; an unchanged cluster MUST NOT be.

**FR-804 [W7]** Each storyline MUST maintain a **state summary**: a bounded running record of facts established so far, capped at a configurable token budget (default 800 tokens).

**FR-805 [W7]** When the state summary exceeds its budget, it MUST be compacted by an LLM call that preserves resolved facts and open questions, discarding superseded detail.

**FR-806 [W7]** Every summary MUST be accompanied by the outbound links of its member articles. Rendering a summary without links is prohibited.

### 2.9 Development detection (FR-900)

**FR-901 [W8]** When a cluster attaches to an existing storyline, the system MUST evaluate whether it constitutes a development: given the storyline's state summary, does this cluster contain information not already established?

**FR-902 [W8]** The detector MUST return either a structured delta (what is new) or an explicit null. Ambiguous or unparseable output MUST be treated as null. Rationale: silence is the safe default.

**FR-903 [W8]** Development detection MUST be folded into the same LLM call as cluster summarization. It MUST NOT add a separate call.

**FR-904 [W8]** Each detected development MUST carry a `significance` score in [0, 1].

**FR-905 [W8]** A detected development MUST update the storyline's state summary. A null result MUST NOT.

**FR-906 [W8]** The system MUST persist the full detector input and output for every evaluation, so that eval scoring and prompt regression testing are possible after the fact.

### 2.10 Interests and ranking (FR-1000)

**FR-1001 [W9]** A Reader MUST be able to express an interest as free text. A fixed topic taxonomy MUST NOT be the primary input mechanism.

**FR-1002 [W9]** Each interest MUST be stored with its embedding, computed by the same model as article embeddings.

**FR-1003 [W9]** Each interest MUST carry a `breadth` value in [0, 1] that maps to a significance/similarity threshold. Low breadth admits only high-significance items; high breadth admits semantically adjacent material.

**FR-1004 [W9]** A Reader MUST be able to follow a specific storyline explicitly. A followed storyline MUST bypass interest-similarity filtering entirely — following is a stronger signal than topical match.

**FR-1005 [W9]** The feed view MUST rank items by a documented function of interest similarity, significance, recency and source count. The function MUST be inspectable.

**FR-1006 [W9]** Every ranked item MUST be able to display why it was surfaced: which interest matched, or which followed storyline it belongs to.

**FR-1007 [W9]** The system MUST display, per interest, the number of feeds currently being watched that plausibly cover it. Implied completeness is prohibited.

**FR-1008 [W9]** Reader feedback (positive/negative on an item) MUST be persisted for later ranking evaluation, whether or not it affects ranking in v1.

### 2.11 Notification gating (FR-1100)

**FR-1101 [W10]** The system MUST enforce a hard per-Reader daily notification budget `K` (default 2, user-configurable, maximum 10).

**FR-1102 [W10]** The gate MUST maintain a rolling distribution of significance scores over a trailing window (default 14 days) and fire only when a candidate exceeds the percentile calibrated to yield approximately `K` notifications per day.

**FR-1103 [W10]** The gate MUST NOT fire on a null development result under any circumstances. Topic matches alone never notify — only developments do.

**FR-1104 [W10]** Every notification MUST include the storyline title, the delta, and a deep link to the storyline timeline.

**FR-1105 [W10]** Every notification MUST be explainable: the Reader MUST be able to see why it cleared the gate.

**FR-1106 [W10]** The system MUST enforce a quiet-hours window (default 22:00–07:00 local) during which notifications are queued, not delivered.

**FR-1107 [W10]** Delivery MUST use Web Push (VAPID). Native mobile push is out of scope.

**FR-1108 [W10]** Notification history MUST be persisted with its significance score and percentile at fire time, for calibration review.

### 2.12 Evaluation harness (FR-1200)

**FR-1201 [W3]** The system MUST provide a labeling export that dumps candidate articles to CSV **sorted by embedding similarity**, so that probable duplicates are adjacent and labeling reduces to "same as previous row."

**FR-1202 [W3]** The system MUST score event clustering against a gold set using B-cubed precision, recall and F1. Rationale: B-cubed is per-element and therefore robust to the extreme cluster-size skew inherent in news.

**FR-1203 [W3]** The system MUST support sweeping `TAU_EVENT` across a range and emitting a threshold-versus-F1 curve as both data and plot.

**FR-1204 [W6]** The system MUST score storyline linking against a gold set over a ≥30-day window using B-cubed, plus pairwise link precision.

**FR-1205 [W8]** The system MUST score development detection as binary classification (development vs. rehash) reporting precision, recall and F1, with precision as the headline metric.

**FR-1206 [W8]** The system MUST score summary faithfulness: the proportion of claims in a generated summary supported by source material. Automated scoring MAY use an LLM judge, but MUST be validated against a human-labeled subset of at least 100 items, with agreement reported.

**FR-1207 [W11]** The system MUST report cost telemetry: dollars per 1,000 articles ingested, dollars per cluster summarized, and projected dollars per Reader per month.

**FR-1208 [W3]** Gold sets MUST be version-controlled in the repository. Eval scripts MUST be runnable by a third party with a single command.

**FR-1209 [W12]** Every threshold constant shipped in configuration MUST have a corresponding entry in the README stating its value and the eval number justifying it.

## 3. Non-functional requirements

### 3.1 Performance

**NFR-101** A full pipeline run over 80 feeds MUST complete in under 5 minutes on a 4-core CPU with no GPU.

**NFR-102** Embedding throughput MUST exceed 200 articles/second on CPU with batching.

**NFR-103** Similarity search over the active window MUST complete in under 50 ms at 50,000 stored articles.

**NFR-104** Page render for the feed view MUST complete in under 500 ms.

### 3.2 Cost

**NFR-201** Total operating cost MUST remain under $5/month at single-Reader scale.

**NFR-202** LLM invocation count MUST scale with cluster volume, not Reader count. Any design breaking this is rejected regardless of quality improvement.

**NFR-203** The system MUST run with zero LLM cost through week 6. LLM integration is deliberately deferred so that clustering can be tuned freely.

### 3.3 Storage and retention

**NFR-301** Articles older than `RETENTION_D` (default 400 days) MUST be prunable, with embeddings dropped first and metadata retained.

**NFR-302** At 1,000 articles/day, 400-day retention implies ~400k articles and ~600 MB of `float32` embeddings at 384 dimensions. The design MUST accommodate this on a single disk without sharding.

### 3.4 Reliability

**NFR-401** A single feed failure MUST NOT abort a pipeline run.

**NFR-402** The pipeline MUST be safely re-runnable at any point after a crash without data corruption or duplicate clusters.

**NFR-403** All pipeline runs MUST be logged with per-stage counts and durations.

### 3.5 Maintainability

**NFR-501** The system MUST require no operated service beyond a cron job, a SQLite file, and a static file server.

**NFR-502** No web framework may be introduced before week 11.

**NFR-503** Every tuned constant MUST live in one configuration module, never inline in logic.

### 3.6 Privacy and legal

**NFR-601** Reader interests, feedback and notification history MUST remain local to the deployment. No third-party analytics.

**NFR-602** Article body text MUST NOT be stored under any circumstances.

**NFR-603** The deployment MUST NOT offer open public registration.

**NFR-604** A documented feed-removal process MUST exist with a 24-hour SLA.

## 4. Data model

```sql
-- Sources and ingestion state
CREATE TABLE source (
  id            INTEGER PRIMARY KEY,
  name          TEXT NOT NULL,
  feed_url      TEXT NOT NULL UNIQUE,
  packs         TEXT NOT NULL,          -- JSON array
  lang          TEXT NOT NULL DEFAULT 'en',
  weight        REAL NOT NULL DEFAULT 1.0,
  enabled       INTEGER NOT NULL DEFAULT 1,
  etag          TEXT,
  last_modified TEXT,
  last_ok_at    TEXT,
  fail_streak   INTEGER NOT NULL DEFAULT 0,
  status        TEXT NOT NULL DEFAULT 'ok'   -- ok | degraded | disabled
);

CREATE TABLE article (
  id                 INTEGER PRIMARY KEY,
  source_id          INTEGER NOT NULL REFERENCES source(id),
  canonical_url      TEXT NOT NULL UNIQUE,
  title              TEXT NOT NULL,
  snippet            TEXT,
  author             TEXT,
  published_at       TEXT NOT NULL,       -- UTC ISO8601
  fetched_at         TEXT NOT NULL,
  timestamp_inferred INTEGER NOT NULL DEFAULT 0,
  simhash            INTEGER,
  embedding          BLOB,                -- float32, L2-normalized
  embed_model        TEXT
);
CREATE INDEX idx_article_pub ON article(published_at);

-- Level 1
CREATE TABLE cluster (
  id              INTEGER PRIMARY KEY,
  canonical_title TEXT NOT NULL,
  centroid        BLOB,
  created_at      TEXT NOT NULL,
  updated_at      TEXT NOT NULL,
  member_count    INTEGER NOT NULL DEFAULT 0,
  distinct_sources INTEGER NOT NULL DEFAULT 0,
  summary         TEXT,                   -- W7
  summary_hash    TEXT,                   -- W7, member-set hash for cache
  storyline_id    INTEGER REFERENCES storyline(id)   -- W5
);
CREATE INDEX idx_cluster_updated ON cluster(updated_at);

CREATE TABLE article_cluster (
  article_id INTEGER NOT NULL REFERENCES article(id),
  cluster_id INTEGER NOT NULL REFERENCES cluster(id),
  PRIMARY KEY (article_id, cluster_id)
);

-- Entities (W4)
CREATE TABLE entity (
  id         INTEGER PRIMARY KEY,
  key        TEXT NOT NULL UNIQUE,   -- canonical identifier
  type       TEXT NOT NULL,          -- PERSON | ORG | GPE | LAW | EVENT | PRODUCT
  doc_freq   INTEGER NOT NULL DEFAULT 0,
  stoplisted INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE entity_alias (
  surface   TEXT NOT NULL,
  entity_id INTEGER NOT NULL REFERENCES entity(id),
  PRIMARY KEY (surface, entity_id)
);

CREATE TABLE cluster_entity (
  cluster_id INTEGER NOT NULL REFERENCES cluster(id),
  entity_id  INTEGER NOT NULL REFERENCES entity(id),
  salience   REAL NOT NULL,
  PRIMARY KEY (cluster_id, entity_id)
);

-- Level 2 (W5)
CREATE TABLE storyline (
  id            INTEGER PRIMARY KEY,
  title         TEXT NOT NULL,
  state_summary TEXT,                    -- W7
  created_at    TEXT NOT NULL,
  last_active_at TEXT NOT NULL,
  status        TEXT NOT NULL DEFAULT 'live',  -- live | dormant | archived
  cluster_count INTEGER NOT NULL DEFAULT 0
);
CREATE INDEX idx_storyline_active ON storyline(last_active_at, status);

CREATE TABLE storyline_entity (
  storyline_id INTEGER NOT NULL REFERENCES storyline(id),
  entity_id    INTEGER NOT NULL REFERENCES entity(id),
  weight       REAL NOT NULL,
  PRIMARY KEY (storyline_id, entity_id)
);

CREATE TABLE storyline_edit (
  id          INTEGER PRIMARY KEY,
  action      TEXT NOT NULL,       -- merge | split | retitle
  payload     TEXT NOT NULL,       -- JSON
  created_at  TEXT NOT NULL
);

-- W8
CREATE TABLE development (
  id           INTEGER PRIMARY KEY,
  storyline_id INTEGER NOT NULL REFERENCES storyline(id),
  cluster_id   INTEGER NOT NULL REFERENCES cluster(id),
  delta_text   TEXT,               -- NULL means "rehash"
  significance REAL,
  detector_in  TEXT NOT NULL,      -- persisted for eval + prompt regression
  detector_out TEXT NOT NULL,
  detected_at  TEXT NOT NULL
);

-- W9
CREATE TABLE reader (
  id         INTEGER PRIMARY KEY,
  handle     TEXT NOT NULL UNIQUE,
  tz         TEXT NOT NULL DEFAULT 'UTC',
  daily_budget INTEGER NOT NULL DEFAULT 2,
  quiet_start TEXT NOT NULL DEFAULT '22:00',
  quiet_end   TEXT NOT NULL DEFAULT '07:00'
);

CREATE TABLE interest (
  id        INTEGER PRIMARY KEY,
  reader_id INTEGER NOT NULL REFERENCES reader(id),
  text      TEXT NOT NULL,
  embedding BLOB,
  breadth   REAL NOT NULL DEFAULT 0.5,
  created_at TEXT NOT NULL
);

CREATE TABLE follow (
  reader_id    INTEGER NOT NULL REFERENCES reader(id),
  storyline_id INTEGER NOT NULL REFERENCES storyline(id),
  created_at   TEXT NOT NULL,
  PRIMARY KEY (reader_id, storyline_id)
);

CREATE TABLE feedback (
  id         INTEGER PRIMARY KEY,
  reader_id  INTEGER NOT NULL REFERENCES reader(id),
  cluster_id INTEGER NOT NULL REFERENCES cluster(id),
  value      INTEGER NOT NULL,    -- -1 | +1
  created_at TEXT NOT NULL
);

-- W10
CREATE TABLE notification (
  id             INTEGER PRIMARY KEY,
  reader_id      INTEGER NOT NULL REFERENCES reader(id),
  development_id INTEGER NOT NULL REFERENCES development(id),
  significance   REAL NOT NULL,
  percentile     REAL NOT NULL,
  queued_at      TEXT NOT NULL,
  sent_at        TEXT,
  reason         TEXT NOT NULL
);

-- Observability
CREATE TABLE run_log (
  id          INTEGER PRIMARY KEY,
  started_at  TEXT NOT NULL,
  finished_at TEXT,
  stage_counts TEXT,   -- JSON
  errors      TEXT
);
```

## 5. Configuration surface

All tunable values live in one module. Shipped defaults are placeholders until eval-justified.

| Constant | Default | Justified by |
|---|---|---|
| `TAU_EVENT` | 0.75 | W3 sweep |
| `ACTIVE_WINDOW_H` | 72 | W3 sweep |
| `SIMHASH_HAMMING` | 3 | W2 spot check |
| `TAU_STORY` | 0.55 | W6 sweep |
| `W_JACCARD` | 0.6 | W6 ablation |
| `W_EMBED` | 0.25 | W6 ablation |
| `W_RECENCY` | 0.15 | W6 ablation |
| `STORYLINE_TTL_D` | 45 | W6 |
| `STATE_TOKEN_BUDGET` | 800 | W7 |
| `SIG_THRESHOLD_PCTL` | calibrated | W10 |
| `DAILY_BUDGET_K` | 2 | product decision |
| `RETENTION_D` | 400 | storage math |

## 6. Acceptance criteria

The system is accepted when all of the following are demonstrable by a third party from a clean clone:

| ID | Criterion |
|---|---|
| **AC-1** | `python -m pipeline.run` ingests all enabled feeds, produces clusters, and writes a static feed page, with zero manual intervention. |
| **AC-2** | `python -m evals.clustering` reproduces the published B-cubed F1 within ±0.02. |
| **AC-3** | `python -m evals.storylines` reproduces the published linking F1 within ±0.03. |
| **AC-4** | `python -m evals.developments` reproduces the published precision/recall within ±0.03. |
| **AC-5** | A storyline page shows a chronological timeline with ≥3 clusters and correctly marks which were developments. |
| **AC-6** | Killing the pipeline mid-run and re-running produces no duplicate clusters and no orphaned rows. |
| **AC-7** | Disabling every feed in `feeds.yaml` and adding a new pack of 10 feeds requires no code change. |
| **AC-8** | Notification log shows the daily budget was never exceeded over a 14-day period. |
| **AC-9** | Every threshold in the config table has a README entry with its justifying number. |
| **AC-10** | No article body text exists anywhere in the database. Verified by schema inspection and a spot check. |

## 7. Deferred (explicitly not v1)

Recorded so they stop being re-litigated:

- Native iOS/Android apps
- Full-text search across articles
- Bias or political-lean scoring
- Multi-language storyline linking (single `lang` per pack in v1)
- Real-time streaming ingestion
- Collaborative or shared storylines
- Automatic feed discovery
- Any recommendation model trained on Reader behavior
- Vector database
- Anything requiring an operated service beyond cron + SQLite + static files
